Poll timestamp anomalies in the updates table

A data-quality question for the contest-stats folks — does anyone know the story behind these?

Status: documented, nothing changed. No rows deleted or edited. These late rows might be a scraper artifact, a late official tally correction, or polls that genuinely stayed open late.

What the issue is

39 matches have an updates row timestamped after the poll's normal closing time. In almost every case the last "normal" row sits right at the close (~23:5x, or ~11:5x / ~19:5x for the contests that ran two polls a day), and then a single extra row appears hours to weeks later with a tiny vote change (usually < 0.5 %). Two cases are weirder — the red rows.

Side effects today: the poll-update graphs for these matches stretch their x-axis to cover the gap (a 24-hour match drawn on, e.g., a 560-hour axis), and the updates tables list the stray row. Final vote totals used elsewhere (the matches table, /node/100) are unaffected — they take the correct close-of-poll figures.

Contest "normal" match length: 24 h for everything except CB VIII (2010), GOTD (2010), CB IX (2013) and half of Rivalry (2011), which ran 12 h matches (two per day).

Notes on the odd ones

  • 1639 (A*) — same pattern as the rest but the late change is larger (~+1,076 / +366, roughly 2 % of the vote) vs the < 0.5 % the others show.
  • 1641 (B) — the whole updates series for this match is broken: ~75 rows stuck near zero votes (751 / 253 at the "close"), then one row jumps to the real result (57,876 / 14,445). The matches table has the correct final. Not a late-blip case; the early rows are the problem.
  • 2066 (B) — Mario vs Joanna Dark. Recorded span is 37.8 h for a 24-h contest: there is an additional ~10 h mid-match gap (an overnight lull in an 81 % blowout) on top of the trailing +8.7 h row. Multiple gaps.

Related but understood — no action needed

  • BGE 2K9 polls 3446, 3456, 3461, 3483, 3486, 3496 — only two update rows each (an early sample + the final); the "gap" is between the only two data points. Sparse records, not anomalies.
  • Summer 2K3 polls 1305, 1337, 1338, 1353 and Spring 2K4 poll 1610 — mid-match sampling holes (~hour 3 → hour 11); the rows after the gap are the real match running to its true end.
  • Spring 2K4 poll 1631 (Vice City vs KOTOR) — a genuine two-day poll; 215 real rows continue past the gap.
  • CB VII poll 3308 (Classic Link vs Young Link) — a genuine 48-hour poll; votes climb normally (4.7k → 95k) across it.
  • CB IX poll 5205 (Tifa vs Cirno) — the Cirno vote purge; the post-gap row is the official post-purge result. Already noted on the graph page.

Options considered (not done)

  • Delete the ~37 trailing rows — rejected for now: the vote counts did change, so those rows may be the real close-of-poll tally rather than junk.
  • Rewrite the trailing timestamp to a few minutes after the scheduled close (00:05 / 12:05) — possible for the obvious Type-A cases; keeps the data, fixes the graph axis. Not done pending Board 8 input on whether that misrepresents anything.
  • Clamp the graph x-axis in code (ignore a row > Nh after the previous one in an otherwise-dense series) — cosmetic, leaves the data untouched.

How this list was built

Detection: any > 6 h gap between consecutive update rows of the same match. False positives (sparse 2-row matches, mid-match sampling holes, genuine multi-day polls) were then sorted out from the trailing-row anomalies by hand.
